先说清楚边界：下面还有 4 项"看着像漏洞"的东西被排除，包括一处 "构造了异常却没 raise"的死代码——静态阅读会误判，实测证明行为是对的。

缺陷 A · 替代文本被当作正则替换模板

re.sub(pattern, repl, text) 的 repl 是替换模板， 会解析反斜杠转义。而 replacement_text 是调用方给的普通文本。代码把它直接传了进去， 同一根因共 6 个调用点 + _common 里 2 处。

replacement_textbeforeoutput beforeafteroutput after
<empty>literal (correct)abliteral (correct)ab
_literal (correct)a_bliteral (correct)a_b
-literal (correct)a-bliteral (correct)a-b
\\crash—literal (correct)a\\b
\\\\silently corrupteda\\bliteral (correct)a\\\\b
\\bsilently corrupteda\x08bliteral (correct)a\\bb
\\tsilently corrupteda\tbliteral (correct)a\\tb

\\x00crash—literal (correct)a\\x00b

为什么这不只是"报错难看"

re.error 的 MRO 只有 Exception → BaseException， 不是 ValueError。但函数文档写着 Raises: ValueError， ValidationError 也确实是它的子类。按文档写 except ValueError 的调用方会直接漏接。

而且类名跨版本会变：3.12 叫 re.error，3.13/3.14 叫 re.PatternError。 任何靠异常名做分派的地方，升级解释器时都会静默失灵。

最隐蔽的是 \g<0>：替换内容等于原匹配内容，净化变成空操作。 sanitize_filename("a?b", replacement_text="\\g<0>") 原样返回 a?b， 而 is_valid_filepath 判它 False——非法字符被吐回，等着落到磁盘上。

修复

新增 escape_replacement_text()，把反斜杠加倍后再交给 re.sub：

def escape_replacement_text(replacement_text: str) -> str:
    # ... docstring ...
    if not replacement_text:
        return replacement_text

    return replacement_text.replace("\\", "\\\\")

空串短路，默认路径只多一次真值判断。没用 lambda m: repl 是因为那会在每次匹配时 多一次 Python 调用；转义是纯字符串操作，且保持原有调用形态，改动面最小。

改之前先确认了没有内部依赖模板语义：全仓 grep '\g<0>' 零命中， 文档与示例也从未提及模板能力，所以改成字面量不破坏任何既有契约。

缺陷 B · 驱动器相对路径被改写为绝对路径

ntpath.splitdrive("C:x.txt") 返回 ("C:", "x.txt")。 原代码把 drive 与分隔符拼回去，C: + \ + x.txt = C:\x.txt——绝对路径。

C:..\..\evil.txtrelativeC:\..\..\evil.txtABSOLUTEC:..\..\evil.txtrelative

后果是 os.path.join 在第二个参数为绝对路径时会丢弃第一个参数。 于是一个本该写进上传目录的相对名，变成了向任意盘符根目录写入的绝对路径： 

BASE = r"C:\srv\uploads"
os.path.join(BASE, sanitize_filepath("D:payload.exe", platform="windows"))
# before:  'D:\payload.exe'             <- BASE 被丢掉，换盘
# after:   'D:payload.exe'                <- 仍是相对名

这还制造了一个自相矛盾：校验器接受输入，净化器却产出校验器拒绝的东西。

修复

拆分 drive 后判定是否为驱动器相对形态（drive 非空、剩余部分非空、且不以分隔符开头）， 若是则不插入分隔符，改为把 drive 直接前缀拼接。绝对路径行为完全不变，由回归测试锁定：

缺陷 C · 多字符替代文本的连续折叠失效

replace_symbol(..., is_replace_consecutive_chars=True) 声称把连续替代字符合并。 单字符有效，多字符无效——因为 f"{re.escape(t)}+" 里的 + 只作用于最后一个字符： 

re.sub(f"{re.escape('ab')}+", ...)   # 得到 ab+ ，+ 只绑 b
re.sub(f"(?:{re.escape('ab')})+", ...) # 得到 (?:ab)+ ，+ 绑整个串

>>> replace_symbol("a---b", "ab", is_replace_consecutive_chars=True)
'aababab'      # 错：应当折叠为 'aab'

这个缺陷独立于 A/B，但同属"正则构造错误"，且上游 4 个既有测试全部只用单字符 _ 做替代符，所以长期没被发现。修 A 时本来就要重写这一行，留着会让"字面量"语义不完整，故一并修。

被排除的四项误报

这一节和上面的修复同样重要。凭代码模式或扫描器告警下判断，这四项都会被误报成漏洞。

已排除 1 · 最重要

构造了 ValidationError 却没 raise

_filepath.py 里有一段创建异常对象后直接丢掉，静态看就是死代码。 实测证明它只是冗余，真正抛错的是后面构造的 err_object，行为完全正确。 只看"造了异常没用"必误报。

已排除 2

净化器不保证输出有效

超长路径（#49）、全点号名字（#69）确实会产出无效值。但这两个 issue 上游已明确讨论并关闭， 补偿机制是 validate_after_sanitize=True（实测确实会抛）。这是向后兼容的默认值选择， 不是遗漏。列为已知限制，不改默认行为。

已排除 3

.. 路径分量原样保留

sanitize_filepath("../../etc/passwd") 默认返回原值。这是既有且刻意的行为—— 净化器不是安全边界。顺手"加固"会破坏大量合法相对路径用法，所以不做，改在风险一节提醒调用方。

已排除 4

替换模板语义本身

改成字面量之前先 grep 了全部 re.sub 调用点与 \g<0>： 零命中，无内部依赖，文档也从未承诺模板能力，因此改动安全。

尚未解决的风险

以下都是已知且刻意不修、或超出本库职责的。不列出来就等于骗人。

净化器不是安全边界高 · 调用方责任

修复后 sanitize_filepath("../../etc/passwd") 仍返回原值。任何"把不可信名字拼到 目录下"的代码都必须自己做 containment 校验（realpath + commonpath）。 本次消除了"本应相对却被改成绝对"这一类绕过，但没有、也不可能把该库变成路径穿越防护层。

默认不保证输出有效中 · 上游设计取舍

超长路径、全点号名字仍可能产出无效值（#49/#69）。需要强保证必须显式开 validate_after_sanitize=True，或自行复验。

替代文本仍可被用于"取消净化"低 · 语义使然

修复后替代文本是纯字面量，但依然原样插入。传 "?" 就能让 a?b 变成 a?b?。转义解决不了这个——替代文本必须是可信的。

非 UTF-8 编码抛 UnicodeEncodeError低 · 既有行为

sanitize_filename("éé", fs_encoding="ascii") 直接抛 UnicodeEncodeError，未包装进 ValidationError。与本次三个缺陷无关， 修它会改变异常类型，需单独的兼容性决策。

仅在 Windows 宿主实测中 · 验证面限制

Linux/macOS 的宿主差异未经真实机器验证。相关逻辑已通过显式 platform= 做平台无关断言，但建议上游 CI 矩阵跑一遍确认。
